# Protected reader performance update

Deploy the existing Render backend from this actual repository, then publish Flutter 1.0.9 (15) through Play internal testing. No database migration or new environment variable is required for this reader update. Existing payment, private storage, Play Integrity and signing settings stay in place.

## Server behavior

The renderer retains one parsed PDF in server RAM only (original input at most 50 MiB). The cached document expires after 10 idle minutes or 30 minutes total and is also cleared on replacement and shutdown; invalid storage privacy is rejected before any cached data is used. Background cleanup runs every 30 seconds. The raw buffer is zeroed when released. Rendered base pages share a 16 MiB LRU pixel budget. PDFBox input/stream caches and JPEG output stay in memory; the optimization introduces no PDF/page disk cache or public endpoint.

Subsequent pages retain purchase, session, device-signature, timestamp, nonce/replay and rate checks before consulting the cache. An optional initial page is bound into the one-time, signed, Play-verified activation proof and counts against the same page rate limit. Older clients and servers keep using the original page endpoint. Bucket privacy is checked even on cache hits, using the current storage.buckets row in the same database query as book access and session validation. The reader no longer calls the storage HTTP metadata endpoint for each page; unknown/inaccessible storage metadata fails closed. The runtime DB role needs SELECT on storage.buckets (the current Supabase postgres role has it). Base rasters stay inside the server; a fresh JPEG is composed with the authenticated reader's watermark for every response, retaining HTTP no-store headers. Watermarks now use two faint diagonal lines at 8 percent opacity plus a compact ownership/session footer outside document content.

## Mobile behavior

Only the current watermarked page is retained in RAM, with no multi-page prefetch or disk cache. Progress restoration starts alongside verification. Successful background renewal keeps the image and zoom; an independent hard-expiry timer wipes and blocks the image if verification cannot finish in time. Permission denial wipes immediately. Recovery retries are bounded with backoff. The hard deadline uses monotonic verification-request age as well as the server expiry, so clock changes and slow responses cannot extend the verified lifetime. Backgrounding, close, stale responses and account changes discard/clear page buffers; reopening still requires verification. The original secure-window/screenshot/recording protection remains in the Android code.

## Verification and limitations

Tests cover download/raster reuse, idle/hard expiration, replacement files, pixel-memory eviction, concurrent render limits, storage privacy failures, reader-specific watermark isolation, warm-cache revocation/replay denial and original stream blocking. Widget tests cover no-blank renewal, hard expiration on outages, permission denial, background/resume, late pages and closure. Visual review uses a synthetic PDF only. The final complete suite passed 115 Flutter tests and 104 backend tests; static analysis reported zero errors/warnings. Both the full backend package and signed Android app bundle were built locally. Live latency and the new Play-installed release still need checking after deployment.

These changes remove repeated download/parse/render work but do not guarantee a specific live latency; the first uncached open still requires Play Integrity, private storage and database access. The single-document cache and single render permit intentionally bound resource use on the small backend instance; a larger multi-reader workload may still need more resources or a separate rendering tier. No DRM system can make visible page pixels impossible to extract from a fully compromised device. The original PDF itself is never provided to the app by this protocol.

## Follow-up latency and price-popup fix

Warm reader access now fetches the book, active purchase, stale-receipt indicator, session key and private-bucket state in one fresh SQL query. A stale Google receipt still invokes the existing server recheck and then reloads current state. No entitlement/role revocation check is cached. The PDF source cache remains one bounded server-only document; its longer source lifetime does not extend any five-minute reader session.

New clients request the current/resumed first page within activation, only when the challenge advertises initial_page_supported. The page number is signed and one-time challenge consumption prevents replay. The returned current-page JPEG is transferred once, unused data is cleared, and existing background/expiry memory cleanup remains. The library reuses its already loaded resume position and refreshes it after returning from the reader. First opens still involve Play Integrity and an uncached original download when necessary.

Price loading is popup-local and per product. Closing the app price preview never prepares a payment journal. Opening another book cannot inherit a stale price request. Actual checkout/pending/verification uncertainty remains protected against duplicate charges. Google Play's empty-product-ID cancellation callback clears only an active checkout without an observed store transaction; genuine pending or legacy uncertain purchases retain recovery state.

The internal AAB enables READER_METRICS: adb logcat can show fixed reader_timing stages, elapsed_ms and optional server_ms only. No token, key, account/book ID, URL, receipt, page content or exception body is logged. The server also returns aggregate Server-Timing for protected reader responses. Deployment and Play installation are required before the new live latency can be measured.
